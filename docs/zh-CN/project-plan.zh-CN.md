## 2. 差异化

### 定位

已决定（D1）。

> **可以核对的提供商切换器。** ccset 通过修补 Agent 自己的配置文件来切换编程 Agent
> 使用的 API 提供商。写入之前给你看确切的改动，自己什么都不留：不建数据库，不留
> 常驻进程，不起代理。

一句话：给编程 Agent 换 API 提供商，改动之前逐行给你看；不建数据库，不起代理，
不留常驻进程。

受众按先后：在桌面应用到不了的地方工作的人（SSH 主机、容器、WSL、CI）；把 Agent
配置放进 dotfiles 的人；需要一条可以放心写进文档的命令的服务商。

### 为什么现在不用「配置即代码」

两份评审对资产和非目标的看法一致，分歧在标题。R2 的「配置即代码」主张更大，本计划
把它留作方向，但不作为现在时的承诺，理由有四条：

1. **它会重犯两份评审开篇指出的错误。** 评审的第一条发现是标语（「Switch」）说了
   产品没做到的事。以 plan、apply、回滚为标题，等于承诺三条还不存在的命令。
2. **需求没有度量过。** R2 把远程和 CI 用户的规模标为假设，并建议在做 `plan`/`apply`
   之前先用 recipe 检验。
3. **`ccset.toml` 会削弱最强的主张。** 一旦有第二个文件来描述配置，「Agent 的文件
   是唯一事实来源」就不再不言自明。只有当这个文件是用户自己持有的输入、ccset 从不
   写它时，这句话才成立。这需要一次明确的设计决定，不能默认如此。
4. **等待没有损失。** 声明式 apply 需要脱敏 diff、凭据引用和全目标预检（F-05）。
   这三项单独拿出来都有用，在本计划里都排在更前面。

### 四条主张，以及让它们看得见的东西

R1 最尖锐的一点是：ccset 的优势全是它*不做*的事，而没做的事是看不见的。所以下面
每条主张都配一样访客可以检查的东西。

| 主张 | 今天是否成立 | 今天是否看得见 | 怎么让人看见 |
| --- | --- | --- | --- |
| 没有第二份配置 | 是 | 否 | README 增加一节，列出 ccset 创建的全部路径（1.2） |
| 写入之前能看到改动 | 部分：`--dry-run` 只列目标，不列行 | 否 | `--dry-run` 和 TUI 审阅界面输出脱敏的逐行 diff（2.1、2.2） |
| 做不到就拒绝，不写一个不会生效的文件 | 是 | 散落在 Codex 指南里 | 一页拒绝情形，每条链接到对应的 fixture（2.3） |
| 可以核实来源和保证 | 是：来源证明、37 个 `verify:*` 脚本、20 篇 ADR | 否 | 来源证明和 CI 徽章；一份写入契约，把每条保证对应到没有它就会失败的 fixture（1.1、2.4） |

「保留注释和自定义键」留在 README 里，作为第一条主张的证据。R1 提到 CC Switch 现在
也这么说，所以它撑不起标题。

### 中立

ccset 不接受赞助，不放联盟链接，不做付费推广，预设和 README 都是如此（D2）。预设是
附带一手来源、经过审核的公开数据，任何人都可以按同样的条件提交。这是第五条主张。
和前四条不同，它是对将来的承诺：说出来容易，收回来代价很高，所以要在 README 写出来
之前先定下来。

### ccset 让出去的

工具数量、预设数量、图形界面、协议转换，以及 MCP 或 Prompts 管理。README 应当点名
把这些用户推荐给 CC Switch。把服务不了的用户让出去，剩下的主张才可信。

2.1 的设计说明。`src/operations/commit.ts` 的 `planTargets` 已经同时持有原文和将要
写入的确切字节，所以生成 diff 不需要再读一次文件。难点是脱敏。常规的 unified diff
会打印上下文行，而改动行的邻居可能是另一个提供商的凭据，或者一个不受管的
`Authorization` 头。只遮住受管的密钥是不够的。安全的默认做法是只显示改动行，遮住
密钥类型的值，上下文只给出所在的表名或键路径。这需要先写 ADR 再写代码，fixture 里
必须有一个紧挨着改动的不受管密钥。

recipe（2.5）有两个用途：它们是 R2 要求的场景文档，也是检验远程和 CI 受众是否
存在的最便宜的办法。

## 4. 不做的事

两份评审对这份清单没有分歧；它本身就是定位的一部分。

- 本地代理、路由、协议转换、故障转移。
- MCP、Skills、Prompts、会话或用量管理。
- 桌面界面或托盘。
- ccset 自有的提供商存储或索引。
- 为了对齐竞品的清单而增加 Agent。新 Agent 以带证据的实现提案进入（F-10）。
- 遥测。用公开信号代替（第 6 节）。
- 赞助商、联盟链接或付费推广（D2）。
- 拼数量的预设目录。预设始终是附带一手来源、经过审核的数据，由需要它的人提交。

**0.4 还差什么。** npm 只能给已经存在的包配置可信发布者（`npm help trust`，
npm 12.2.1，2026-11-13 查阅），所以 `publish.yml` 无法创建 `ccset`。需要由登录了
npm 的维护者从 `packages/ccset/` 发布第一个版本，再允许本仓库的 `publish.yml`
和 `npm-publish` 环境为该包运行 `npm publish`。之后的版本通过
`ccset-v<version>` 标签发布。手动发布哪个版本由维护者决定：先发布一个临时
版本，0.1.0 就能带来源证明，转发包的发布任务也能第一次实际运行；直接发布
0.1.0 则少一步。

在名称注册之前，`packages/ccset/README.md` 里写着一条任何人都可以抢注的
`npx ccset` 命令。这正是 D3 要消除的风险，而且现在已经在公开仓库里可见。

转发包在同一进程中导入已安装的 CLI，并固定依赖一个已发布的确切版本。主包每次
发布后，更新该依赖和两份转发包 README，重新验证，再发布转发包。主包的标签是
`v<version>`，转发包是 `ccset-v<version>`。两者都通过 `publish.yml`，使用
`npm-publish` 环境、可信发布和来源证明。发布检查拒绝属于另一个包的标签、
版本不符的标签、本地发布，以及不干净的工作区。

0.11.0 已在 npm 上，阶段 1 要写进文档的命令现在都可以安装，阶段 1 不再等待
阶段 0。在 0.4 注册无作用域名称之前，安装命令仍用 `npx @droite/ccset`。

发布说明已随 v0.11.0 Release 公布，取代原先放在这里的草稿。验证结果记录在
只追加的
[Important Documentation.md §9](<../../Important Documentation.md#9-implementation-register-code-complete>)
的 9.74 到 9.76 条目中。
